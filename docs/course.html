01

Plan before codeתוכנית לפני קוד

commitsקומיטים a960608RESTGit

Before writing a single line of code, we wrote PLAN.md, a short document that records every important decision. What happens when you delete a project? (Its issues are deleted too.) What kind of IDs do we use? (Random UUIDs.) Can an issue move to another project? (No.) Answering these questions first means we don't have to rewrite code later.

לפני שכתבנו שורת קוד אחת, כתבנו את PLAN.md: מסמך קצר שמתעד כל החלטה חשובה. מה קורה כשמוחקים פרויקט? (גם הסוגיות שלו נמחקות.) באיזה סוג מזהים משתמשים? (UUID אקראי.) האם אפשר להעביר סוגיה לפרויקט אחר? (לא.) כשעונים על השאלות האלה מראש, לא צריך לשכתב קוד אחר כך.

What we builtמה בנינו

  • A decisions table covering IDs, updates, cascade delete, unique names and Hebrew support
  • The full list of 12 endpoints and the 4 error codes
  • A testing strategy and a build order, which this course follows
  • טבלת החלטות: מזהים, עדכונים, מחיקה מדורגת, שמות ייחודיים ותמיכה בעברית
  • הרשימה המלאה של 12 נקודות הקצה ו-4 קודי השגיאה
  • אסטרטגיית בדיקות וסדר בנייה, שהקורס הזה הולך לפיו

Key ideaרעיון מרכזי

A plan is cheap to change. Code is expensive to change. Make the hard decisions on paper.

קל לשנות תוכנית. יקר לשנות קוד. את ההחלטות הקשות מקבלים על הנייר.

Go deeper: PUT vs PATCHלהרחבה: PUT מול PATCH

One decision in the plan was to support both kinds of update. PATCH changes only the fields you send. PUT replaces the whole object, so any optional field you leave out is cleared. Writing this down early meant both the code and the tests had one clear rule to follow.

אחת ההחלטות בתוכנית הייתה לתמוך בשני סוגי עדכון. PATCH משנה רק את השדות ששולחים. PUT מחליף את כל האובייקט, כך שכל שדה אופציונלי שלא נשלח נמחק. כשזה כתוב מראש, גם לקוד וגם לבדיקות יש חוק אחד וברור.

02

Set up the monorepoהקמת ה-monorepo

commitsקומיטים 02656a8b1380344eaff5f370a1ednpm workspacesTypeScriptESLintPrettierVitestCLAUDE.md

A monorepo is one repository that holds several packages. TaskForge has three server packages: shared, storage and api. The UI joined them later as client. npm workspaces links the packages, so api can import @taskforge/shared by name, as if it came from npm.

Monorepo הוא ריפוזיטורי אחד שמחזיק כמה חבילות. ל-TaskForge יש שלוש חבילות שרת: shared, storage ו-api. ממשק המשתמש הצטרף אחר כך בתור client. npm workspaces מקשר בין החבילות, כך ש-api יכול לייבא את @taskforge/shared לפי שם, כאילו הגיע מ-npm.

We also set the house rules on day one: strict TypeScript, ESLint and Prettier for clean code, Vitest for tests, and CLAUDE.md, a file that tells every developer (human or AI) how to work in this repo.

ביום הראשון קבענו גם את חוקי הבית: TypeScript במצב strict, ‏ESLint ו-Prettier לקוד נקי, Vitest לבדיקות, ו-CLAUDE.md, קובץ שמסביר לכל מפתח (אדם או AI) איך עובדים בפרויקט. 

package.json{
  "type": "module",
  "workspaces": ["server/*", "client"],
  "scripts": {
    "test": "vitest run",
    "typecheck": "tsc -b && …",
    "lint": "eslint ."

Key ideaרעיון מרכזי

Dependencies point one way: api → storage → shared. Lower layers never import upper ones, so each layer can be tested alone.

התלויות הולכות בכיוון אחד: api → storage → shared. שכבה נמוכה אף פעם לא מייבאת שכבה גבוהה ממנה, ולכן אפשר לבדוק כל שכבה לבד.

Go deeper: why pin exact versions?להרחבה: למה לנעול גרסאות מדויקות?

Every dependency is pinned to an exact version, like "express": "5.3.0", with no ^. Everyone who installs the project gets the same code, so a bug can't appear just because a library released a new version overnight. Upgrades happen on purpose, one at a time.

כל תלות נעולה לגרסה מדויקת, למשל "express": "5.3.0", בלי ^. כל מי שמתקין את הפרויקט מקבל בדיוק אותו קוד, כך שבאג לא יופיע רק כי ספרייה שחררה גרסה חדשה בלילה. שדרוגים קורים בכוונה, אחד בכל פעם.

Two small fix commits followed: one stopped Vitest from forcing an import condition on its workers, and one allowed a lint pattern (const { id, ...rest } = obj) used to drop fields. Setup work always needs a little tuning.

אחרי זה הגיעו שני קומיטים קטנים של תיקון: אחד מנע מ-Vitest לכפות תנאי ייבוא על התהליכים שלו, ואחד אישר תבנית lint ‏(const { id, ...rest } = obj) שמשמשת להשמטת שדות. הקמה תמיד צריכה קצת כיוונון.

Shared types and validation rulesטיפוסים וחוקי ולידציה משותפים

commitsקומיטים 91aead4TypeScriptzod

The shared package describes the world of TaskForge. Types say what a Project and an Issue look like. zod schemas check that data coming from outside is valid. For example, a project name can't be empty or longer than 100 characters, and a request can't include unknown fields.

החבילה shared מתארת את העולם של TaskForge. טיפוסים (types) מגדירים איך נראים פרויקט וסוגיה. סכמות zod בודקות שמידע שמגיע מבחוץ תקין. למשל, שם פרויקט לא יכול להיות ריק או ארוך מ-100 תווים, ובקשה לא יכולה לכלול שדות לא מוכרים. 

server/shared/src/schemas/project.ts// POST body. Strict, so id / timestamps cannot be set by clients.
export const createProjectSchema = z.strictObject({
  name: requiredText(TEXT_LIMITS.name),          // trimmed, NFC, 1–100 chars
  description: optionalText(TEXT_LIMITS.description),
});

What we builtמה בנינו

  • domain.ts: Project, Issue, statuses open / in_progress / closed, priorities low / medium / high
  • Schemas for create (POST), replace (PUT), patch (PATCH) and list queries
  • ErrorCode: VALIDATION_ERROR, NOT_FOUND, CONFLICT, INTERNAL_ERROR
  • domain.ts: פרויקט, סוגיה, סטטוסים open / in_progress / closed, עדיפויות low / medium / high
  • סכמות ליצירה (POST), להחלפה (PUT), לעדכון חלקי (PATCH) ולשאילתות רשימה
  • ErrorCode: ‏VALIDATION_ERROR, NOT_FOUND, CONFLICT, INTERNAL_ERROR

Key ideaרעיון מרכזי

TypeScript checks your code while you write it. zod checks the data while the program runs. You need both.

TypeScript בודק את הקוד בזמן הכתיבה. zod בודק את המידע בזמן הריצה. צריך את שניהם.

Go deeper: "as const" instead of enumלהרחבה: ‏as const במקום enum

The project doesn't use TypeScript's enum, because Node.js runs .ts files directly by simply erasing the types, and an enum is not just a type. Instead we write a plain array and derive the type from it:

הפרויקט לא משתמש ב-enum של TypeScript, כי Node.js מריץ קבצי .ts ישירות פשוט על ידי מחיקת הטיפוסים, ו-enum הוא לא רק טיפוס. במקום זה כותבים מערך רגיל ומפיקים ממנו את הטיפוס:

04

Hebrew and two languagesעברית ושתי שפות

commitsקומיטים c7f12ad481cc88Unicode & Intlzod

TaskForge speaks Hebrew properly. Every message the user can see lives in two catalogs, messages.en.ts and messages.he.ts. When a request sends the header Accept-Language: he, errors come back in Hebrew. A custom zod error map even translates the validation errors.

TaskForge מדברת עברית כמו שצריך. כל הודעה שהמשתמש יכול לראות נמצאת בשני קטלוגים: messages.en.ts ו-messages.he.ts. כשבקשה שולחת את הכותרת Accept-Language: he, השגיאות חוזרות בעברית. מפת שגיאות מותאמת של zod מתרגמת אפילו את שגיאות הוולידציה. 

POST /projects  ·  Accept-Language: he  →  409{
  "error": {
    "code": "CONFLICT",
    "message": "פרויקט בשם \"אתר החברה\" כבר קיים"
  }
}

Hebrew text needs care in three more places. Text is normalized to NFC, so the same word typed two ways is stored the same way. Lengths are counted in code points, so a letter with nikud or an emoji isn't counted twice. Sorting uses Intl.Collator, so Hebrew titles come out in alphabet order.

טקסט בעברית צריך תשומת לב בעוד שלושה מקומות. הטקסט מנורמל ל-NFC, כך שאותה מילה שהוקלדה בשתי דרכים נשמרת אותו דבר. האורך נספר ב-code points, כך שאות עם ניקוד או אימוג'י לא נספרים פעמיים. המיון משתמש ב-Intl.Collator, כך שכותרות בעברית יוצאות לפי סדר האלף-בית.

05

Storage behind interfacesאחסון מאחורי ממשקים

commitsקומיטים 480154aRepository patternVitest

The rest of the code never talks to a database or a file directly. It talks to a repository interface, a list of promises like "find this project" or "save this issue". Then we can swap how data is stored without touching the business logic.

שאר הקוד אף פעם לא מדבר ישירות עם מסד נתונים או קובץ. הוא מדבר עם ממשק repository, רשימה של הבטחות כמו "מצא את הפרויקט הזה" או "שמור את הסוגיה הזאת". כך אפשר להחליף את צורת האחסון בלי לגעת בלוגיקה העסקית. 

server/storage/src/types.ts (simplified)interface ProjectRepository {
  list(opts: ListOptions<'name'>): Promise<Page<Project>>;
  findById(id: string): Promise<Project | null>;
  create(project: Project): Promise<Project>;
  delete(id: string): Promise<boolean>;
}

The first implementation keeps everything in memory, which is fast and great for tests. We also wrote contract tests: one test suite that any implementation must pass. Later the JSON-file version ran the exact same suite.

המימוש הראשון שומר הכול בזיכרון: מהיר ומצוין לבדיקות. כתבנו גם בדיקות חוזה (contract tests): סט בדיקות אחד שכל מימוש חייב לעבור. מאוחר יותר גרסת קובץ ה-JSON הריצה בדיוק את אותו סט.

Key ideaרעיון מרכזי

Program against an interface. If you add SQLite tomorrow, it only has to pass the same contract tests.

כותבים קוד מול ממשק. אם מחר מוסיפים SQLite, הוא רק צריך לעבור את אותן בדיקות חוזה.

06

Errors and middlewareשגיאות ו-middleware

commitsקומיטים b847f55Express 5zod

In Express, a middleware is a function that every request passes through, like a checkpoint. TaskForge has four: locale picks Hebrew or English, validate runs the zod schemas, notFound catches unknown URLs, and errorHandler turns any error into a clean JSON answer.

ב-Express, middleware הוא פונקציה שכל בקשה עוברת דרכה, כמו מחסום בדיקה. ב-TaskForge יש ארבעה: locale בוחר עברית או אנגלית, validate מריץ את סכמות ה-zod, notFound תופס כתובות לא מוכרות, ו-errorHandler הופך כל שגיאה לתשובת JSON נקייה. 

server/api/src/errors/app-error.tsexport class NotFoundError extends AppError {
  static project(id: string): NotFoundError {
    return new NotFoundError('error.notFound.project', { id });
  }
}
// A service just throws: the central handler builds the 404 response.
throw NotFoundError.project(projectId);

Key ideaרעיון מרכזי

One place builds every error response. Services only throw. That keeps errors consistent and never leaks a stack trace to the user.

    Glossaryמילון מונחים

    API
    A set of URLs a program can call to read or change data.
    אוסף כתובות שתוכנה יכולה לקרוא להן כדי לקרוא או לשנות מידע.
    Endpoint
    One URL plus one HTTP verb, like POST /projects.
    כתובת אחת ופועל HTTP אחד, למשל POST /projects.
    Middleware
    A function every request passes through on the way to its route.
    פונקציה שכל בקשה עוברת דרכה בדרך ל-route שלה.
    Schema
    A description of valid data, used to check input.
    תיאור של מידע תקין, שמשמש לבדיקת קלט.
    Cascade delete
    Deleting a parent also deletes its children (project → issues).
    מחיקת הורה מוחקת גם את הילדים שלו (פרויקט ← סוגיות).
    Atomic write
    A save that either fully happens or doesn't happen at all.
    שמירה שקורית במלואה או לא קורית בכלל.
    Optimistic update
    Show the change first, confirm with the server after, and undo if it fails.
    מציגים את השינוי קודם, מאשרים מול השרת אחר כך, ומבטלים אם נכשל.
    Contract test
    One test suite that every implementation of an interface must pass.
    סט בדיקות אחד שכל מימוש של ממשק חייב לעבור.
    E2E
    End-to-end: testing the full app through a real browser.
    קצה לקצה: בדיקה של כל האפליקציה דרך דפדפן אמיתי.
    Design token
    A named design value (a color, a size, a duration) stored as a CSS variable.
    ערך עיצוב עם שם (צבע, גודל, משך) שנשמר כמשתנה CSS.
    Locale
    The user's language and region, like he or en.
    השפה והאזור של המשתמש, למשל he או en.
    Pull Request
    A request to merge a branch, where changes are reviewed first.
    בקשה למזג ענף, שבה השינויים נסקרים קודם.
